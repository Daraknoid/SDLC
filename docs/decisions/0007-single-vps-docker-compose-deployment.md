# Развёртывание — один VPS на объект, Docker Compose, образы из GitHub Container Registry

## Контекст и постановка задачи

Заказчик предоставляет VPS с Docker и доменом (AS-4), бюджет на эксплуатацию — не дороже 15 USD в месяц (SRS 3.5.7), установка должна занимать не более 15 минут (REQ-INST-001). Как развёртывать и обновлять систему?

## Драйверы решения

* REQ-INST-001: `docker compose up -d` на чистом сервере.
* REQ-BUILD-001: сборка образов в GitHub Actions.
* REQ-SEC-002: TLS 1.2+, HSTS; БД не доступна извне.
* REQ-AVAIL-001: 99,5 % в часы работы, плановые работы ночью.

## Рассмотренные варианты

* Docker Compose на одном VPS
* Kubernetes (k3s)
* PaaS (Render, Railway) с управляемой PostgreSQL

## Итог решения

Выбранный вариант: «Docker Compose на одном VPS», потому что он покрывает требования по нагрузке, укладывается в бюджет и не требует от заказчика компетенций в оркестрации. Контейнеры: `nginx` (TLS, статика), `api`, `db`, `backup`; наружу открыты только порты 80 и 443.

### Последствия

* Хорошо, потому что обновление — `docker compose pull && docker compose up -d` (простой менее 30 с ночью).
* Хорошо, потому что окружение разработки совпадает с промышленным.
* Плохо, потому что VPS — единая точка отказа; смягчается ежедневным `pg_dump` с хранением вне VPS и инструкцией восстановления (RTO 1 ч).

### Подтверждение

Демонстрация установки по README на чистом VPS (REQ-INST-001); проверка SSL Labs не ниже A (REQ-SEC-002); `docker compose config` в CI.

## Плюсы и минусы вариантов

### Docker Compose

* Хорошо, потому что минимальный порог входа и стоимость.
* Плохо, потому что нет автоматического переключения при отказе узла.

### Kubernetes

* Хорошо, потому что самовосстановление и масштабирование.
* Плохо, потому что избыточен для 3 контейнеров и требует администрирования.

### PaaS

* Хорошо, потому что не нужно администрировать сервер.
* Плохо, потому что стоимость с управляемой БД выше бюджета и противоречит AS-4.
