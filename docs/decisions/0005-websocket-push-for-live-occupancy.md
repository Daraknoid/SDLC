# Обновление live-графика — push по WebSocket, в релизе 1–2 только за текущие сутки

## Контекст и постановка задачи

Администратор должен видеть заполняемость с задержкой не более 2 с (BG-3, REQ-FUNC-009), сканеры — получать предупреждение о заполнении (REQ-FUNC-010). Как доставлять изменения клиентам? По итогам первого раунда обсуждения с заказчиком (27.10.2026) объём функции сокращён: история за 7 дней и догрузка пропущенных данных перенесены в релиз 3 (функция F20).

## Драйверы решения

* BG-3: задержка ≤ 2 с; REQ-INT-006: сообщение не позже 1 с после ответа на `/validate`.
* REQ-REL-003: автоматическое переподключение.
* Срок и бюджет: оценка функции F11 снижена с 32 до 20 ч.

## Рассмотренные варианты

* WebSocket (`ws` в процессе API)
* Server-Sent Events
* Периодический опрос REST каждую секунду

## Итог решения

Выбранный вариант: «WebSocket», потому что он уже зафиксирован в контракте REQ-INT-006, даёт задержку в десятки миллисекунд и позволяет в одном соединении передавать и счётчик, и ленту событий. При переподключении клиент заново запрашивает данные за текущие сутки (`GET /api/v1/occupancy/today`) вместо догрузки только пропущенного интервала.

### Последствия

* Хорошо, потому что 20 панелей и 50 сканеров дают постоянную нагрузку, близкую к нулю, в отличие от опроса (70 запросов/с).
* Хорошо, потому что упрощённая схема «перезапросить сутки» не требует хранения курсора событий.
* Плохо, потому что nginx нужно настроить на проксирование `Upgrade`, а соединения — на ping/pong каждые 25 с.
* Нейтрально, потому что при одном процессе API рассылка выполняется в памяти; при масштабировании потребуется брокер (PostgreSQL `LISTEN/NOTIFY`).

### Подтверждение

Тест `tests/api/ws-occupancy.test.ts`: подписанный клиент получает сообщение не позже 1 с после ответа `/validate`; e2e-проверка переподключения после перезапуска контейнера `api`.

## Плюсы и минусы вариантов

### WebSocket

* Хорошо, потому что двунаправленный канал и минимальная задержка.
* Плохо, потому что сложнее отладка и прокси.

### Server-Sent Events

* Хорошо, потому что простая реализация поверх HTTP, встроенное переподключение.
* Нейтрально, потому что однонаправленный канал достаточен для графика.
* Плохо, потому что ограничение 6 соединений на домен в HTTP/1.1 для вкладок панели.

### Опрос REST

* Хорошо, потому что проще всего.
* Плохо, потому что задержка до интервала опроса и лишняя нагрузка на API и БД.
