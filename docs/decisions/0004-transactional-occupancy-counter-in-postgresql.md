# Счётчик заполняемости — строка PostgreSQL, изменяемая в транзакции валидации

## Контекст и постановка задачи

На одном объекте одновременно работают до 4 сканеров. Две валидации, пришедшие одновременно, не должны оба пропустить человека сверх вместимости (REQ-FUNC-010) или дважды пропустить один пропуск (REQ-FUNC-006), а счётчик должен совпадать с журналом (REQ-REL-002). Где хранить счётчик и как синхронизировать параллельные проверки?

## Драйверы решения

* REQ-REL-002: решение, событие и счётчик — атомарно.
* REQ-PERF-001: p95 ≤ 500 мс при 20 запросах/с.
* Минимум компонентов в развёртывании (ADR-0001, ADR-0007).

## Рассмотренные варианты

* Строка `site_counter` с блокировкой `SELECT … FOR UPDATE` в транзакции валидации
* Счётчик в Redis (`INCR`/`DECR`)
* Вычисление числа людей внутри запросом по журналу при каждой проверке

## Итог решения

Выбранный вариант: «Строка `site_counter` с блокировкой», потому что это единственный вариант, при котором счётчик, присутствие и событие меняются одной ACID-транзакцией без дополнительной инфраструктуры. Блокировка сериализует проверки только в пределах одного объекта, что при 20 запросах/с даёт ожидание в единицы миллисекунд.

### Последствия

* Хорошо, потому что расхождение счётчика и журнала невозможно по построению.
* Хорошо, потому что не нужен Redis — меньше контейнеров и точек отказа.
* Плохо, потому что пропускная способность одного объекта ограничена последовательной обработкой (оценочно свыше 300 проверок/с — с запасом).
* Нейтрально, потому что рассылка в WebSocket выполняется после `COMMIT`, чтобы клиенты не видели отменённые изменения.

### Подтверждение

Интеграционный тест `tests/integration/concurrency.test.ts`: 10 000 параллельных валидаций, после чего счётчик равен разности входов и выходов в журнале; нагрузочный тест k6 (F18) подтверждает REQ-PERF-001.

## Плюсы и минусы вариантов

### Строка с блокировкой

* Хорошо, потому что строгая согласованность.
* Плохо, потому что «горячая» строка при очень большой нагрузке.

### Redis

* Хорошо, потому что очень быстрые атомарные операции.
* Плохо, потому что нет общей транзакции с PostgreSQL — нужны компенсации при сбое.
* Плохо, потому что ещё один контейнер и его резервное копирование.

### Вычисление по журналу

* Хорошо, потому что нет отдельного состояния.
* Плохо, потому что запрос по растущему журналу (до 2 млн событий) замедляется и всё равно требует блокировки от гонок.
