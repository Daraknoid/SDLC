# Фото владельцев пропусков — файлы на томе Docker, выдача только через API

## Контекст и постановка задачи

Во втором раунде обсуждения (28.10.2026) заказчик добавил функцию F22 «Фото владельца на пропуске»: контролёр сверяет лицо человека с фото на карточке результата, чтобы пропуск нельзя было передать другому (BG-2, новое требование REQ-FUNC-015). Фото — персональные данные (CON-5, REQ-SEC-005-2). Где хранить фото и как отдавать их сканеру?

## Драйверы решения

* REQ-PERF-002: фото не должно увеличивать время до решения более чем на 200 мс.
* CON-5: доступ только у авторизованных контролёров и администраторов, удаление по запросу.
* Бюджет: без платных хранилищ (SRS 3.5.7).
* До 10 000 пропусков (REQ-PERF-003).

## Рассмотренные варианты

* Файлы JPEG на томе Docker `photos`, выдача через API с проверкой сессии
* Поле `bytea` в PostgreSQL
* Объектное хранилище S3

## Итог решения

Выбранный вариант: «Файлы на томе Docker», потому что 10 000 фото по ~40 КБ (480×480, JPEG качество 80) занимают около 400 МБ, а выдача файла через `api` с проверкой роли проще и быстрее, чем чтение из БД. Имя файла — случайный UUID, ссылка на него хранится в `holder.photo_id`.

### Последствия

* Хорошо, потому что база данных не растёт, резервное копирование фото — простой `rsync` тома.
* Хорошо, потому что сканер получает фото отдельным запросом `GET /api/v1/photos/{id}` параллельно с отображением решения и кэширует его на время смены.
* Плохо, потому что файлы и БД не в одной транзакции — удаление выполняется в два шага с повторной очисткой «осиротевших» файлов задачей F17.
* Нейтрально, потому что сохраняется только по явному согласию (`holder.photo_consent_at`).

### Подтверждение

Тесты F22: загрузка, сжатие до 480×480, запрет доступа без сессии (401) и для чужого объекта (403), удаление фото при удалении владельца.

## Плюсы и минусы вариантов

### Том Docker

* Хорошо, потому что просто и дёшево.
* Плохо, потому что привязка к одному серверу (как и вся система, ADR-0007).

### PostgreSQL `bytea`

* Хорошо, потому что транзакционное удаление.
* Плохо, потому что раздувает базу и резервные копии в разы.

### S3

* Хорошо, потому что масштабируемость.
* Плохо, потому что внешний платный сервис и передача персональных данных третьей стороне.

## Дополнительная информация

Затрагивает представления SDD 004-information, 005-interface и 009-deployment; функции F22 и F17 бэклога.
