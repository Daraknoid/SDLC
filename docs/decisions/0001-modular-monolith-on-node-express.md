# Серверная часть — модульный монолит на Node.js и Express

## Контекст и постановка задачи

Сервер QRGate должен валидировать пропуска (REQ-FUNC-004), управлять пропусками и объектами, рассылать события в реальном времени (REQ-INT-006) и выполнять фоновые задачи (REQ-FUNC-013, REQ-SEC-005-2). Нагрузка небольшая: до 20 запросов валидации в секунду и 50 сканеров (REQ-PERF-001, REQ-PERF-003). Разработку ведёт один разработчик (позже — с junior), развёртывание — один VPS на объект (раздел 3.5.3 SRS). Как разбить серверную часть на развёртываемые единицы?

## Драйверы решения

* Срок: релиз 2.0 к 25.12.2026 силами 1–2 разработчиков.
* Ограничение CON-2: TypeScript, Node.js 20 LTS, Express.
* Целостность: решение, событие и счётчик в одной транзакции (REQ-REL-002).
* Простота установки у заказчика одной командой (REQ-INST-001).
* Повторное использование модуля токенов для будущих турникетов (SRS 3.5.5).

## Рассмотренные варианты

* Модульный монолит (один процесс, модули с явными интерфейсами)
* Микросервисы (валидация, пропуска, realtime — отдельные сервисы)
* Serverless-функции облачного провайдера

## Итог решения

Выбранный вариант: «Модульный монолит», потому что он единственный обеспечивает атомарность валидации одной локальной транзакцией без распределённых протоколов и укладывается в срок и состав команды.

### Последствия

* Хорошо, потому что одна сборка, один контейнер `api`, простая отладка и развёртывание.
* Хорошо, потому что вызовы между модулями — функции в процессе, без сетевых задержек (бюджет REQ-PERF-001).
* Плохо, потому что масштабирование только вертикальное; для 3 корпусов это допустимо (REQ-PERF-003).
* Плохо, потому что модули легко «срастаются»; требуется дисциплина границ (см. «Подтверждение»).

### Подтверждение

ESLint-правило `import/no-restricted-paths`: модуль может импортировать другой модуль только через его `index.ts`; пакет `qr-token` не зависит от Express и БД. Проверка выполняется в CI (REQ-BUILD-001).

## Плюсы и минусы вариантов

### Модульный монолит

* Хорошо, потому что транзакция БД покрывает всю валидацию (REQ-REL-002).
* Хорошо, потому что минимальные затраты на инфраструктуру.
* Нейтрально, потому что границы модулей позволяют позже выделить сервис.
* Плохо, потому что отказ процесса останавливает все функции (смягчается рестартом Docker и мониторингом).

### Микросервисы

* Хорошо, потому что независимое масштабирование и развёртывание.
* Плохо, потому что согласованность счётчика между сервисами требует саг или распределённых блокировок.
* Плохо, потому что для одного разработчика объём инфраструктурной работы превышает срок.

### Serverless-функции

* Хорошо, потому что не нужно администрировать сервер.
* Плохо, потому что долгоживущие WebSocket-соединения и cron-задачи требуют дополнительных сервисов провайдера.
* Плохо, потому что противоречит допущению AS-4 (заказчик предоставляет VPS) и бюджету 3.5.7 SRS.
